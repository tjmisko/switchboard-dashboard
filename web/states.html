field guide

Every session gets one lamp.
Here is what it is actually reporting.

Switchboard watches your Claude Code sessions and puts a colored chip on your bar for each one. The color is not a mood and not a guess — it is the output of a small, total function over everything Switchboard currently believes about that session. This page walks that function backwards, from the lamp you can see to the evidence underneath it.

If you only read one thing, read the five lamps in the short version — that is the whole contract. If you have ever wondered why a chip was green while nothing seemed to be happening, or red long after you answered, the answer is in §4 and §5.

    One lamp, several workers

    A Claude Code session is not one worker. It is 1 + N writers: the main thread, plus every subagent currently in flight. They share a process, a transcript path, and one chip — and each of them can block on its own permission prompt, independently of the others.

    • “Is the agent working?” is not a well-formed question. There are several agents behind one chip.
    • Green can mean the main thread stopped a minute ago and three teammates are still going. That is not a bug; it is the whole point of delegating.
    • Red can belong to a subagent you never started by hand — and answering it unblocks work you cannot see.

    no memory — by construction

    The color must not have memory. Memory in the color layer is a latch, and a latch that drifts out of step with the world is exactly what stale red and false green are the names of.

    What a writer can be

    Seven states. Each one is a claim about a single writer — never about the session — and each contributes a color to the fold in §5.

    the pair that makes the model click

    ToolInFlight unmatched tool_use in the tail
    identical on disk
    Blocked unmatched tool_use in the tail

    A tool that is merely running and a tool that is waiting for your approval leave exactly the same mark in the transcript. The only thing that ever separates them is a single PermissionRequest hook — which fires once, on the edge, and never repeats.

    Three things the rest of this page needs fall straight out of that:

    1. Blocked is the only state that cannot be rebuilt by reading files — so it is the only one that has to survive a daemon restart.
    2. The transcript can only ever say “ToolInFlight or Blocked.” That makes it a falsifier, never a source.
    3. Leaving Blocked needs the negation of that shared mark — every dispatched tool matched. Anything weaker cannot tell the twins apart, so it cannot prove your prompt was answered.

    The third is a live defect in the shipped daemon. It is in §7, named and measured.

    How it finds out

    Switchboard never asks an agent how it is doing. It observes. Everything it knows arrives as one of thirteen kinds of evidence, from one of three sources — and the source is what bounds how much a kind is allowed to prove.

    Hover any kind for what it means. The two marked key are the load-bearing ones: one is the only way into Blocked, the other the only sound way out.

    two rules that apply from every state

    • Gone → Dead — the process exited, or the subagent was force-closed. Absorbing: nothing comes back from here.
    • SessionRotated → Unknown — a /clear or a fork changed the session id under the same pid, so every prompt recorded against the old id died with it.

    They are pulled out here rather than repeated in all seven rows below, which is also how the model itself states them.

    The fold

    Layer 3. Six rungs, checked in order, first match wins. No memory, no special cases, and — importantly — nothing here knows or cares whether a writer is the main thread or a subagent.

      Red outranks everything because a pending prompt is the only actionable thing a chip can carry. A quick decision unblocks real work; “work is happening” asks nothing of you. So a prompt anywhere in the session tree beats any amount of work anywhere in it.

      what this abstraction buys

      An earlier model carried “in-flight subagents” as a dimension, alongside the main thread's state and the pending-prompt count — five rows of case table and two named rules just to reconcile them. Here a live teammate is simply a writer that is Working, so “delegating” is not a state, not a rule, and not a special case. It is the ordinary green rung, reached with the main thread in Ended. It survives only as a badge on the verdict, for a tooltip that wants to say how many.

      Back on the timeline

      The dashboard colors its swimlanes with the same six outcomes, under older names that predate this model. Here is the mapping, so a bar you are staring at can be read as a claim about writers.

      The one worth internalizing is dormant. A dormant parent is not idle and not stuck — it has handed off, and the solid green underneath it belongs to the subagent doing the work. Time spent dormant is delegated time, which is why the dashboard counts it as leverage rather than waste.

      Where the model and the daemon disagree

      This page describes the specification. The daemon shipping today does not implement all of it. Those are defects, not design choices, and they are listed rather than smoothed over — a page that quietly described the intended behavior would be worse than no page, because it would make a real bug unfalsifiable.

      Four transitions nothing implements
