What the status colors mean

Switchboard puts one colored chip on the bar for each coding-agent session, and the whole model is meant to be read from across the room. Green is work running. Orange is a session that has stopped and wants a new prompt. Red is a decision of yours blocking work that could be running.

The color is computed, not guessed — a total function over everything Switchboard currently believes about the session. The first four sections are what an operator needs; the reference half is the model underneath, for changing the daemon or writing a provider.

    The six lane colors

    Every bar on the dashboard is one of six statuses. This is not dashboard slang — it is the wire vocabulary of the provider contract, which every source emits. The rest of the page is where a color comes from.

    dormant is the one worth internalizing: the session handed off, and the green underneath belongs to the subagent. Dormant time is delegated time, which is why the dashboard counts it as leverage.

    One chip, several writers

    A session is 1 + N writers: the main thread plus every subagent in flight, sharing one process, one log, one chip. Each can block on its own permission prompt.

    • Green can mean the main thread stopped a minute ago while three subagents run on.
    • Red can belong to a subagent you never started by hand. It costs the same keystroke to clear and unblocks work you cannot see.

    Only the per-writer machine in §7 has memory. The chip is a pure function of the writer → state map, memoryless by construction, because a latch in the color layer is what stale red and false green are made of.

    How the chip is chosen

    Six rungs, first match wins. Nothing here knows a main thread from a subagent.

      Why red sits above green

      The rungs rank by what it costs you to leave a session alone.

      red — a cheap decision is holding up expensive work

      Approval or a one-line answer, and behind it a chain of work that would otherwise run unattended. The best return on a second of your time.

      clear it now

      green — work is happening

      Asks nothing of you. Interrupting it costs more than it returns.

      leave it

      orange — the session wants real input

      A new prompt, a review, a decision you have to think about. Nothing here was going to proceed without you, so leaving it costs only the delay — batching orange to protect a block of focus is often the right trade.

      When the chip is wrong

      The daemon does not implement all of the model below. The one that will bite you: a red can clear before you actually answered — measured at 5s into a prompt that stayed unanswered for another 3m07s. Your terminal is the source of truth.

      Both divergences and four unimplemented transitions, with cell coordinates and rule ids, are in §8.

      What a writer can be

      Seven states. Each is a claim about a single writer, never about the session.

      the ambiguity at the center of the model

      ToolInFlight unmatched tool_use in the tail
      identical on disk
      Blocked unmatched tool_use in the tail

      A tool that is merely running and one waiting for your approval leave the same mark in the log. Only a permission notification separates them, and it fires once, on the edge. This is the general case, not a quirk of one agent: on Codex a gated call is byte-identical to a running one with no recovery from the file at all. Three invariants follow:

      1. Blocked cannot be rebuilt by reading files, so it is the one state that has to survive a daemon restart.
      2. The log can only ever say “ToolInFlight or Blocked.” It can falsify a belief; it can never establish one.
      3. Leaving Blocked needs the negation of that shared mark — every dispatched tool matched. Anything weaker cannot tell the twins apart, so it cannot prove your prompt was answered. The shipped daemon breaks this one (§8).

      How it finds out

      Switchboard observes; it never asks an agent how it is doing. Three sources, and the source bounds what evidence from it can prove. The sources are the general shape; what fills them is per agent, and two agent kinds ship today.

      So a provider that announces nothing about permission can never paint red — no log distinguishes a gated tool from a running one. Of the writer-driven colors it reaches only green, orange and gray; suspended and hidden still work, because those are liveness rungs above the machine and read the process rather than the agent. That is a tier limit rather than a bug, and a source with no status concept at all is legitimate too: the contract accepts one working interval spanning the lifetime.

      The thirteen kinds the Claude adapter supplies. Hover for meaning; the two marked key are load-bearing. Codex announces the same events but does not persist approvals, so it cannot supply the sound exit from Blocked and falls back to the cap.

      two rules that apply from every state

      • Gone → Dead — the process exited, or the subagent was force-closed.
      • SessionRotated → Unknown — a context reset or fork changed the session id under the same pid, retiring every prompt recorded against the old one.

      The machine

      All 6 live states × 11 kinds of evidence — 66 cells, no defaults; an unlisted cell throws rather than guessing. Evidence is attributed to a writer by the caller, so the machine assumes routing already happened and cross-writer bugs live outside it.

      Four transitions nothing implements

      All four are ToolInFlight cells: the daemon has no representation of that state, which is why it cannot tell a tool waiting on you from one waiting on a machine. Their rule ids mean the edge fires, not that the daemon can occupy the state.
