field guide

What the status colors mean

Switchboard puts one colored chip on the bar for each coding-agent session, and the whole model is meant to be read from across the room. Red is a decision of yours blocking work that could be running. Green is work running. Orange is a session that has stopped and wants a new prompt.

The color is computed: a small total function over everything Switchboard currently believes about that session. This page walks that function backwards, from the chip to the evidence underneath it. For why a chip was green with nothing apparently happening, or red long after you answered, see §4 and §5.

    One chip, several writers

    A session is 1 + N writers: the main thread plus every subagent in flight. They share a process, a transcript path, and one chip. Each can block on its own permission prompt, independently of the others.

    • “Is the agent working?” has no single answer. Several writers sit behind one chip.
    • Green can mean the main thread stopped a minute ago while three subagents run on. That is delegation working.
    • Red can belong to a subagent you never started by hand. It costs the same keystroke to clear and unblocks work you cannot see, so treat it exactly like the main thread's.

    no memory — by construction

    The color layer must have no memory. Memory there is a latch, and a latch that drifts out of step with the world produces stale red and false green.

    What a writer can be

    Seven states. Each is a claim about a single writer, never about the session, and each contributes a color to the fold in §5.

    the ambiguity at the center of the model

    ToolInFlight unmatched tool_use in the tail
    identical on disk
    Blocked unmatched tool_use in the tail

    A tool that is merely running and a tool that is waiting for your approval leave the same mark in the transcript. The only thing separating them is a single PermissionRequest hook, which fires once, on the edge, and never repeats.

    Three things the rest of this page needs fall out of that:

    1. Blocked cannot be rebuilt by reading files, so it is the one state that has to survive a daemon restart.
    2. The transcript can only ever say “ToolInFlight or Blocked.” It can falsify a belief; it can never establish one.
    3. Leaving Blocked needs the negation of that shared mark — every dispatched tool matched. Anything weaker cannot tell the twins apart, so it cannot prove your prompt was answered.

    The third is a live defect in the shipped daemon, named and measured in §7.

    How it finds out

    Switchboard observes; it never asks an agent how it is doing. Everything it knows arrives as one of thirteen kinds of evidence from one of three sources, and the source bounds how much a kind is allowed to prove.

    Hover any kind for what it means. The two marked key are load-bearing: one is the only way into Blocked, the other the only sound way out.

    two rules that apply from every state

    • Gone → Dead — the process exited, or the subagent was force-closed. Absorbing: nothing comes back from here.
    • SessionRotated → Unknown — a /clear or a fork changed the session id under the same pid, so every prompt recorded against the old id died with it.

    The fold

    Layer 3. Six rungs, checked in order, first match wins. No memory, no special cases, and nothing here knows whether a writer is the main thread or a subagent.

      Why red sits above green

      The order is a claim about what your attention is worth, not about what is most interesting. Rungs 3 to 6 rank by what it costs you to leave a session alone.

      red — a cheap decision is holding up expensive work

      Approval or a one-line answer, and behind it a chain of work that would otherwise have run unattended. The best return on a second of your time on the board. A subagent's red costs the same to clear and is just as expensive to leave.

      clear it now

      green — work is happening

      Asks nothing of you. Interrupting it costs more than it returns.

      leave it

      orange — the session wants real input

      A new prompt, a review, a decision you have to think about. Nothing was going to proceed here without you, so the cost of letting it sit is the delay alone. Batching orange to protect a block of your own focus is often the right trade.

      what this abstraction buys

      An earlier model carried in-flight subagents as a separate dimension, alongside the main thread's state and the pending-prompt count — five rows of case table and two named rules to reconcile them. Here a live subagent is simply a writer that is Working, so “delegating” is not a state, a rule, or a special case. It is the ordinary green rung, reached with the main thread in Ended. It survives only as a badge on the verdict, for a tooltip that wants to say how many.

      Back on the timeline

      The dashboard colors its swimlanes with the same six outcomes, under older names that predate this model. Here is the mapping, so a bar you are staring at can be read as a claim about writers.

      The one worth internalizing is dormant. A dormant parent has handed off, and the solid green underneath it belongs to the subagent doing the work. Dormant time is delegated time, which is why the dashboard counts it as leverage.

      Where the model and the daemon disagree

      This page describes the specification. The daemon shipping today does not implement all of it. Those are defects, and they are listed rather than smoothed over: a page that quietly described the intended behavior would make a real bug unfalsifiable.

      Two cells behave differently in practice

      Four transitions nothing implements

      All four are ToolInFlight cells. That is the finding: the daemon has no representation of that state at all, which is why it cannot tell a tool waiting on you from a tool waiting on a machine.
